# Uptime Kuma heartbeat

`codex-usage-monitor.service` sends a best-effort success heartbeat to an Uptime Kuma **Push** monitor after `codex_usage_monitor.py once` exits successfully.

## Secret configuration

Store the Push URL only in the existing private environment file:

```text
CODEX_USAGE_KUMA_PUSH_URL=https://<kuma-host>/api/push/<push-token>
```

Do not commit the real URL/token. The helper accepts the URL generated by Kuma even when it already contains `status`, `msg`, or `ping` query parameters; those values are normalized before sending.

## Kuma monitor

Create one Push monitor named `codex-usage-monitor`. The systemd timer runs every 15 minutes, so configure Kuma with enough tolerance for timer accuracy and acquisition latency; 20 minutes is a reasonable starting heartbeat interval.

The helper sends `status=up` and `msg=codex-usage-monitor cycle ok`. It validates Kuma's JSON response and never prints the secret Push URL. Delivery is intentionally best-effort: a Kuma outage does not turn a successful Codex quota acquisition into a failed systemd unit. A failed or non-running collector produces no heartbeat, so Kuma detects it by expiry.

## Manual verification

After the Push URL is configured:

```bash
python3 uptime_kuma_push.py --strict --message "manual heartbeat test"
systemctl --user daemon-reload
systemctl --user start codex-usage-monitor.service
systemctl --user status codex-usage-monitor.service --no-pager
```

Use `--strict` only for explicit verification. The systemd service intentionally uses the default best-effort behavior.
