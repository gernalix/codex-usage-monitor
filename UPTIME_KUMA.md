# Uptime Kuma heartbeat

`codex-usage-monitor.service` runs on the Fedora workstation and sends a best-effort success heartbeat to an Uptime Kuma **Push** monitor after `codex_usage_monitor.py once` exits successfully.

Uptime Kuma may remain hosted on the Oracle VM because it is genuinely always-on infrastructure. The Codex collector itself must not run on that VM: quota acquisition and session/publisher work are Fedora-local.

## Secret configuration

Store the Push URL only in the existing private Fedora environment file:

```text
/home/daniele/.config/codex-usage-monitor/codex-usage-monitor.env
```

with:

```text
CODEX_USAGE_KUMA_PUSH_URL=https://<kuma-host>/api/push/<push-token>
```

Do not commit the real URL/token. The helper accepts the URL generated by Kuma even when it already contains `status`, `msg`, or `ping` query parameters; those values are normalized before sending.

## Kuma monitor

Create one Push monitor named `codex-usage-monitor`. The Fedora systemd timer runs every 15 minutes, so configure Kuma with enough tolerance for timer accuracy and acquisition latency; 20 minutes is a reasonable starting heartbeat interval while the workstation is expected to be online.

The helper sends `status=up` and `msg=codex-usage-monitor cycle ok`. It validates Kuma's JSON response and never prints the secret Push URL. Delivery is intentionally best-effort: a Kuma outage does not turn a successful Codex quota acquisition into a failed systemd unit.

Because Fedora is not an always-on server, Kuma downtime alerts for this monitor should be interpreted in the context of workstation availability. The Oracle VM must not run a duplicate collector merely to keep this heartbeat continuously green.

## Manual verification

After the Push URL is configured on Fedora:

```bash
python3 uptime_kuma_push.py --strict --message "manual heartbeat test"
systemctl --user daemon-reload
systemctl --user start codex-usage-monitor.service
systemctl --user status codex-usage-monitor.service --no-pager
```

Use `--strict` only for explicit verification. The systemd service intentionally uses the default best-effort behavior.
